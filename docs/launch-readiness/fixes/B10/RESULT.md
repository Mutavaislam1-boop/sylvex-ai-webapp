## 1. SQL-инъекции (S1-06, подпункт `sql_injection`)

Что было у Codex: точечная проверка шаблонов высокого риска без находок; «81 место динамического SQL полностью не проверено».

Что сделано: AST-сканер (`evidence/sql_scan.py`) нашёл все вызовы `execute` / `executemany` / `mogrify`, у которых текст запроса не литерал. Сканировались все `.py` файлы, кроме tests, scripts, migrations и офлайн-инструментов нагрузки.

| Код | Нелитеральных мест | Файл со списком |
|---|---|---|
| API 5dbcde1: main.py + services | 129 | `evidence/sql_sites_api_5dbcde1.txt` |
| API: worker.py, routers, backend, db_pool и прочее | 0 | — |
| Воркеры dde6dea | 109 | `evidence/sql_sites_workers_dde6dea.txt` |

У воркеров нет ни одного места, которого нет в API. Codex считал 81 место по более узкому шаблону, AST-сканер нашёл 129, просмотрены все.

Классы подстановок в текст SQL. Все проверены по месту построения:
- Константы модуля: интервалы TTL, `STORAGE_ID_FLOOR`, списки колонок `_REFERENCE_COLUMNS`, `_ADMIN_COLUMNS`, `_COLUMNS`, `VALID_ENTITLEMENT_SQL`, `PROSTUDIO_QUEUE_CHANNEL`.
- Имена колонок и фрагменты WHERE из фиксированных кортежей или белых списков, а значения передаются через `%s`:
  - `_admin_generation_where`;
  - фильтры references и аналитики;
  - фильтры тредов поддержки и сегментов рассылок;
  - журнал аудита админки;
  - `user_access._where`;
  - `reviews`, `assistant_store`.
- Поиск (ILIKE) всегда параметризован: `%s` со значением `f"%{query}%"`.
- `SET` при обновлении references собирается из ключей фиксированного словаря `fields`.
- Идентификаторы из каталога БД:
  - erasure: `ident()` с `IDENTIFIER.fullmatch`, иначе `erasure_schema_requires_review`;
  - `pk_name` из information_schema в кавычках;
  - `account_identity`: `psycopg2.sql.Identifier`.
- Обёртки `_row`, `streamed_json`, `_run`, `request_row` вызываются только с литеральными запросами.
- `ORDER BY`, `LIMIT`, `OFFSET` не берутся из запроса: `limit` и `offset` приводятся через `int()` с ограничением, а `pinned_order` — константа.

**Результат:** ни в одном месте значение из HTTP-запроса, initData, сессии или webhook не попадает в текст SQL. Находок нет.

Это полный статический обзор, а не динамический fuzz.

### Каналы входа (код 5dbcde1)

| Канал | Чем подтверждается личность | Второй фактор | Critical-действия |
|---|---|---|---|
| Браузер `/api/admin/v2/auth/web` | email + пароль SYLVEX | **TOTP обязателен**. Без TOTP — `totp_enrollment_required`, кроме bootstrap-владельца с подтверждённым `ADMIN_OWNER_EMAIL`, который сразу заводит TOTP. 5 ошибок → блок на 15 мин. | повторный TOTP в течение 5 мин |
| Mini App `/api/admin/v2/auth/telegram` | подпись Telegram initData (≤ 3600 с) → аккаунт → активная запись admin_accounts | **нет** (фактор — сам Telegram-аккаунт) | повторный вход: свежий initData того же Telegram-пользователя |
| Старый Mini App v1 (`miniapp_legacy`, initData в теле запроса) | подпись initData (≤ 3600 с) | **нет** | **повторного подтверждения нет** |
| Бот / Support Bot (`bot`, `ADMIN_SERVICE_TOKEN` + `telegram_id` отправителя) | токен сервиса + Telegram id | **нет** | владелец — без повторного подтверждения; не-владелец — не выше HIGH |

Общие ограничения:
- Ни один Telegram id сам по себе не даёт прав. Нужна активная строка `admin_accounts`; старый обход `SUPERADMIN_TELEGRAM_ID` удалён и используется только для первичного создания владельца и для оповещений.
- Права проверяются по RBAC на каждом маршруте.
- Сессии: 30 мин простоя / 8 ч максимум.
- Журнал аудита только на добавление.

### Вывод

- RBAC и запрет доступа без активной записи администратора подтверждены кодом и 102 тестами.
- Требование «MFA для администраторов» выполнено только для браузерного входа.
- Во всех Telegram-каналах (Mini App v2, Mini App v1, бот) единственный фактор — владение Telegram-аккаунтом администратора.
- В каналах v1 и бот Critical-действия выполняются без повторного подтверждения (для бота — только у владельца). Среди маршрутов v1 к Critical относятся `models.edit`, `broadcast.send` и `admins.permissions.edit`.
- Это осознанное решение в коде, а не обход прав. Но требование MFA для этих каналов не выполнено.
- Администратор без TOTP (по данным Codex от 07.11: 3 активных, TOTP у 2) не может войти через браузер, но имеет полный доступ своей роли через Telegram.

### Чего не хватает (доказательств нет в этой сессии)

1. **Текущее состояние администраторов в БД.** Чтение строки подключения Postgres заблокировано политикой сессии. Запрос только для чтения: `owner_admin_mfa_readonly.sql`.
2. **Включена ли двухэтапная аутентификация Telegram у администраторов.** Проверить можно только в их Telegram: Настройки → Конфиденциальность → Облачный пароль.
3. **Реальный read-only admin smoke.** Нужен вход администратора; из сессии недоступно (прокси блокирует сайт и API).
