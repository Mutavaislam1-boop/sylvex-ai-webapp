# S7-04 — почему `telegram_account_not_found` для 7772859187 (11.11.2026)

Только чтение кода (API b244195, бот 55e57da) и журналов Railway. База, подписки и Production не менялись.

## Что ответил API

`GET /api/admin/v2/erasure/telegram?telegram_id=7772859187` → `"blocker": "telegram_account_not_found"`.

## Где ищет обработчик удаления

`services/telegram_erasure.check_scope`:

```sql
SELECT account_id, origin, … FROM sylvex_accounts WHERE active_telegram_id = %s
```

Нужна строка идентичности SYLVEX ID (`sylvex_accounts`). Этого требует и сам обработчик B09-WEB: `accept_confirmed_request` работает по `account_id`.

## Как этот же человек определяется в Mini App и в боте

- **Mini App, бот, баланс, подписки, генерации:** по `users.telegram_id` и таблицам с `telegram_id`. Строка в `sylvex_accounts` им не нужна. Поэтому человек пользуется сервисом полностью: 317 ⚡, подписка, генерации 02.11, сегодня 14:35Z в Mini App.
- **SYLVEX ID для Telegram-пользователя** (`sylvex_accounts`, origin `telegram`) создаётся только:
  1. триггером `sylvex_users_ensure_account` при **вставке** строки `users`. Триггер добавлен 22.10.2026 (b82e391);
  2. разовым скриптом `scripts/backfill_telegram_sylvex_ids.py` для тех, кто был раньше. Скрипт запускается вручную: по умолчанию пробный режим, запись — с `--execute`.
- При обычной активности строка не создаётся. `ensure_telegram_account` вызывается только для администраторов.

## Установленная причина

- Аккаунт 7772859187 впервые появился **21.10.2026** — на день раньше триггера. Его строка `users` вставлена до появления триггера, а разовое заполнение в Production, судя по результату, не запускалось.
- У него нет строки `sylvex_accounts`, поэтому нет и SYLVEX ID.
- Это не расхождение Telegram ID и внутреннего ID: строки просто нет. Будь аккаунт объединён с сайтом или ID указывал бы на другую запись, ответ был бы `not_a_telegram_account` или `telegram_scope_requires_review`.

Подтверждение без доступа к БД: в консоли (Пользователи → 7772859187) поле **SYLVEX ID будет «—»**.

## Касается ли других

Да. Всем Telegram-пользователям, впервые пришедшим **до 22.10.2026**, это не помешает пользоваться сервисом. Но:
- у них нет SYLVEX ID;
- удаление по запросу через поддержку (S7-04) для них сейчас невозможно: тот же ответ `telegram_account_not_found`.

Точное число покажет пробный запуск скрипта: «Telegram-only users without a SYLVEX ID: N».

## Минимальное исправление — данные, не код

Запустить существующий проверенный скрипт:
- пишет только недостающие строки `sylvex_accounts` (origin `telegram`);
- `created_at` берётся из `users.created_at`, поэтому старые медиа пройдут через инвентаризацию обработчика удаления;
- существующие строки, аккаунты сайта, балансы, генерации и платежи не трогает;
- батчи по 500 с паузой и `lock_timeout` 5 с; можно остановить и повторить.

```
# из корня sylvex-ai-webapp, с доступом к БД (например, railway run)
DATABASE_PUBLIC_URL=... python3 scripts/backfill_telegram_sylvex_ids.py            # 1) пробный: только число
DATABASE_PUBLIC_URL=... python3 scripts/backfill_telegram_sylvex_ids.py --execute  # 2) запись, по разрешению
```

После этого проверка готовности для 7772859187 должна вернуть `blocker: null` или настоящее препятствие (например, `stars_renewal_active`).

Не рекомендуется точечный вызов `SELECT sylvex_ensure_telegram_account(7772859187)`: он ставит `created_at = NOW()`, и обработчик удаления сочтёт аккаунт новым — старые медиа без отметки владельца могут остаться в хранилище.

**Видимый эффект:** у затронутых пользователей появится SYLVEX ID (формат SS 0626 99 NNNN) в профиле и в консоли. Больше ничего не меняется.
