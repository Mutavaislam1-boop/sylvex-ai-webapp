## Что изменено
1. **Списание и `completed` в одной транзакции.**
   - Тело `settle_generation` вынесено в `settle_generation_in(cur, ...)` без изменения логики LR-002.
   - `update_prostudio_generation_job(..., settle=...)` выполняет списание в той же транзакции, что запись `completed` и постановка в очередь R2.
   - Либо коммитится всё вместе, либо ничего.
2. **Результат провайдера не теряется.**
   - До списания результат сохраняется на ещё активном задании (`result_json.completion_checkpoint`).
   - Клиенты читают поля верхнего уровня только после `completed`, поэтому ничего нового не видят.
   - Запись `completed` повторяется до 4 раз (0,5 → 1 → 2 с).
   - Если запись так и не прошла, задание остаётся активным. Восстановление зависших заданий завершает его из контрольной точки, тоже одной транзакцией.
   - Если и это невозможно, задание переходит в `failed`, резерв возвращается.
3. **Однократный возврат для старого порядка.**
   - Случай: `failed` при резерве `charged` (воркер на прежнем коде во время выкатки, или сбой до исправления).
   - Кредиты возвращаются один раз, ограничитель — переход резерва `charged` → `refunded`.
   - Строка в `generation_charges` остаётся как запись аудита.
   - Защита финальных статусов не даёт `completed` стать `failed`, поэтому возврат не может сработать для завершённого задания.
4. **Схема БД не меняется.** Новых колонок и миграций нет. Добавлено новое значение статуса резерва `refunded`; другой код проверяет только `reserved`.

## Ограничения (для решения владельца)
- **Создание персонажа и объекта** по-прежнему списывает до `completed`. Сам персонаж или объект к этому моменту уже сохранён в библиотеке, поэтому результат не теряется. Если запись `completed` не пройдёт, восстановление переведёт задание в `failed` и один раз вернёт кредиты: пользователь сохранит ресурс без оплаты. Объединение этих шагов в одну транзакцию оставлено как отдельное решение.
- **Возвращённое списание остаётся в `generation_charges`.** Поэтому в истории расходов пользователя оно видно как расход.
- **Пока задание активно,** его владелец через опрос задания видит контрольную точку, включая временную ссылку провайдера, во вложенном ключе.

## Дополнение: поздние результаты провайдера (случай Kling)

**Причина.**
- Задание Kling превысило общий лимит 480 с, перешло в `failed`, удержание вернулось.
- Запись `failed` заменяла `result_json` на `{}` (`_safe_json_dumps(None)` → `"{}"`) и стирала `task_id` провайдера.
- Поэтому забрать поздний результат было уже невозможно.
- Кроме того, один вызов опроса Kling сам ждёт до 120 × 5 с, то есть дольше лимита задания.

**Исправление** (`716f755` / `e166989`, изменения в API и workers идентичны):
1. **Ссылка на задачу сохраняется.** Если задание в `provider_processing` падает по таймауту (общий лимит или восстановление зависших), ссылка на задачу провайдера записывается в `error_json.late_result_watch`.
   - Срок наблюдения — 24 ч.
   - Клиенту поле не отдаётся: публичная ошибка пропускает только поля из белого списка.
2. **Фоновый поздний опрос** в пуле воркеров:
   - раз в минуту, захватывает по одному заданию;
   - готовый результат переводит задание `failed` → `completed` один раз, под блокировкой строки;
   - **без списания**: удержание уже вернули, резерв, кошелёк и `generation_charges` не трогаются;
   - результат уходит в очередь R2;
   - задача ещё выполняется — повтор через минуту;
   - 5 неудачных опросов подряд или истёкший срок — наблюдение закрывается.
3. **История, диалог, история персонажа и Telegram** вынесены в `deliver_completed_prostudio_job()`.
   - Её вызывает обычное завершение воркера.
   - Для позднего результата и для завершения из контрольной точки после сбоя её вызывает очередь R2 после сохранения медиа, по одноразовому флагу `delivery_pending`. Флаг снимается по первичному ключу.
   - Обычное завершение доставляется один раз, своим воркером.

**Тесты.** Новые: 8; весь файл `tests/test_b15_completion_atomicity.py` — 22/22 на API и workers.
- Поздний MP4 доставлен: `completed`, без списания, баланс 100, в R2, история 1 раз, Telegram 1 раз.
- Повторный проход и повторная доставка ничего не меняют.
- Задача ещё выполняется — повторный опрос; провайдер сообщает о сбое — наблюдение закрыто после 5 опросов.
- Ошибка провайдера (не таймаут) и таймаут без принятой задачи не наблюдаются.
- Истёкшее наблюдение не опрашивается.
- 4 параллельных прохода: один опрос, одно завершение.
- Падение воркера во время опроса → восстановление → поздняя доставка.
- Завершение из контрольной точки после сбоя доходит до истории и Telegram, списание одно.
- Обычное завершение доставляется один раз.

**Связанные наборы:**
- SQL-восстановление R2 (11/11), история и Telegram, этапы, таймауты, опрос видео — без новых падений.
- Остались только давние падения: 2 устаревших теста R2 и 4 теста с устаревшими фикстурами.

**Ограничения:**
- Поздний результат доставляется бесплатно: SYLVEX оплачивает провайдера, пользователю кредиты уже вернули.
- Применяется только после окончательного возврата: по сбою статуса или по исчерпанию срока ожидания (см. ниже).


## Дополнение 2: лимит 480 с при работающем провайдере

Изменения (`5dbcde1` / `dde6dea`) в API и workers идентичны.

**Если провайдер принял задание** (`provider_processing`, есть `task_id`) и на 480 с отвечает `submitted` / `processing`:
- рабочий слот и слот провайдера освобождаются;
- задание остаётся активным, с пометкой `result_json.background_wait` и сроком ожидания 25 мин после передачи (≈ 33 мин всего);
- удержание кредитов сохраняется, сообщения об ошибке нет, возврата нет.

**Фоновый опрос** (тот же цикл, раз в минуту, одно задание за раз):

| Ответ провайдера | Итог |
|---|---|
| Готово | цена по результату провайдера, одно списание вместе с `completed` (атомарность B15), R2, затем история и Telegram |
| Провайдер сообщил о сбое | `failed`, возврат один раз, уведомление |
| Истёк срок, или 5 сбоев статуса подряд | `failed` с `generation_timeout`, возврат один раз, уведомление; задача остаётся под 24-часовым наблюдением за поздним результатом (доставка без списания) |
| Не хватает баланса при списании | `failed`, удержание возвращено |

Прочее:
- **Восстановление зависших заданий** не трогает задание в фоновом ожидании до его срока, а после срока завершает его с возвратом.
- **Задание, которое провайдер ещё не принял,** на 480 с завершается как раньше: `failed` и возврат.

**Тесты.** Весь файл — 31/31 на API и workers, из них 9 новых. Используется настоящая обёртка лимита (с лимитом 1 с) и настоящий слот провайдера.
- Передача в фон без `failed`, без возврата и без уведомления; слот занят во время опроса и свободен после передачи; восстановление зависших заданий его пропускает.
- Успех: одно списание, R2, история 1 раз, Telegram 1 раз; повторные проходы ничего не меняют.
- Сбой у провайдера: возврат и уведомление.
- Истёк срок: возврат, затем поздний результат доставлен без списания.
- 5 сбоев статуса подряд.
- Восстановление после истечения срока.
- 4 параллельных прохода: один опрос, одно списание.
- Нехватка баланса.
- Задание, ещё не принятое провайдером, завершается по-старому.

**Связанные наборы** (таймаут, восстановление зависших, опрос видео, уведомления, слоты, устойчивость к сбоям провайдера, S7-05): 55 PASS. Остались только 4 давних падения на устаревших фикстурах.
