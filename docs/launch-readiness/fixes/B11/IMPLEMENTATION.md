- Детекторы только читают таблицы `prostudio_generation_jobs` и `prostudio_provider_circuits`.

## План развёртывания (только с разрешения владельца)

1. **API, без изменения поведения.** Fast-forward `release/sx010-api-20261108` 9a6dedc → 7a35c7f. Проверка Railway: SUCCESS, `Application startup complete`, `/health/ready` 200. Оповещения выключены, пока нет `OPS_ALERTS_ENABLED=1`.
2. **Проверить существующую доставку и получателя.** Владелец открывает `GET /api/admin/v2/ops/alerts` (через консоль или я сверяю по логам и его скриншоту): доставка платёжных уведомлений, последние 4 цифры чата. Владелец подтверждает получателя.
3. **Тестовое сообщение после согласования получателя.** `POST /api/admin/v2/ops/alerts/test`, владелец, в консоли. Владелец подтверждает получение; в `ops_alert_deliveries` запись `test ok`.
4. **Включить** `OPS_ALERTS_ENABLED=1` у API (переменная; деплой). В логах должно появиться `OPS ALERTS WORKER STARTED`. Если чат должен быть другим — `OPS_ALERT_CHAT_ID`.
5. **Внешняя проверка.**
   - Владелец добавляет секреты репозитория `OPS_TELEGRAM_BOT_TOKEN` (бот, которым получатель уже пользовался — нажимал /start) и `OPS_TELEGRAM_CHAT_ID`. Секреты владелец вводит сам, в отчёты они не попадают.
   - Слить `tools/ops_uptime_check.py` и `.github/workflows/ops-uptime.yml` в `main` (Railway из `main` не развёртывает).
   - Actions → ops-uptime → Run workflow → `mode: test`: владелец подтверждает получение.
   - Дальше запуск идёт по расписанию.

Откат:
- API — снять `OPS_ALERTS_ENABLED` (оповещения выключаются, код безопасен) или Rollback на деплой с 9a6dedc;
- внешняя проверка — отключить workflow в Actions.

Таблицы `ops_alert_*` старому коду не мешают.

## Ограничения

1. **Внешняя проверка зависит от расписания GitHub.** Запуски могут задерживаться (до 10–15 мин в часы нагрузки). В публичном репозитории расписание отключается после 60 дней без активности. Для частоты 1 мин нужен внешний сервис мониторинга (решение владельца).
2. **Простой воркеров при пустой очереди не обнаруживается:** у воркеров нет собственного heartbeat, сигнал появляется, только когда есть задания. Чтобы ловить и такой простой, нужен heartbeat в воркерах — изменение воркеров, отдельное решение.
3. **Боты (основной и поддержки) не отслеживаются.** Они работают через polling без HTTP; для них нужен heartbeat в боте.
4. **Встроенные оповещения работают, пока работает API;** его падение покрывает только внешняя проверка. Канал один — Telegram. Запасной канал (письмо GitHub) есть только у внешней проверки.
5. **Порог попыток взят из настройки API.** Детектор «очередь стоит» использует `PROSTUDIO_MAX_JOB_ATTEMPTS` API (по умолчанию 3). У воркеров эта переменная задана отдельно; если её значение больше 3, задания с 3+ попытками не попадут в сигнал. Рекомендуется задать одинаковое значение у API.
6. **Пороги** (5 мин, 10 мин, 5 ошибок / 50%, 6 ч) — начальные. Меняются переменными `OPS_ALERT_*` без изменения кода.
7. **Stripe, разборы возвратов и удаление аккаунтов** не входят: Stripe в тестовом режиме (B07).
