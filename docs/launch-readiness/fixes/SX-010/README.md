# SX-010 / B14 — проверка покупок без даты (только чтение)

Файл: `production_readonly_checks.sql`. Запросы подготовлены заново 09.11: исходный файл пропал вместе с архивом. Добавлены источники, найденные в коде, который сейчас работает в Production.

## Как запускать
- Весь файл целиком. Он открывает `BEGIN TRANSACTION READ ONLY`, ставит тайм-аут 30 с и заканчивается `ROLLBACK`.
- Где запускать:
  - Railway → Postgres → Data;
  - или `railway connect Postgres`, затем `\i production_readonly_checks.sql`.
- Строку подключения и пароль в чат не вставлять.
- Результат содержит только агрегаты: нет `telegram_id`, `charge_id`, payload, id заказов и сумм по пользователям.

## Что проверяет каждый запрос
1. **Схема.**
   - Тип, DEFAULT и NULLABLE у `purchases.created_at`; есть ли UNIQUE-индекс на `charge_id`.
   - Наличие и типы всех колонок-источников.
   - Часовой пояс базы. Время сравнивается как UTC; если пояс не UTC, это нужно учесть.
2. **Состав записей без даты.**
   - Разбивка по провайдеру, статусу и валюте.
   - NULL и пустая строка отдельно; число разных `charge_id` и записей без него.
   - Сколько записей ссылаются на заказ `sylvex_order:<id>` или на `stripe_invoice:`.
   - Итог по завершённым должен сойтись с 72 из отчёта 07.11.
3. **Можно ли восстановить дату.** Для каждой записи ищутся первичные источники и проверяется, согласны ли они. Строки делятся на семь непересекающихся групп, их сумма равна числу записей без даты:
   - b1 — `charge_id` у нескольких покупок: не восстанавливать;
   - b2 — `charge_id` и payload указывают на разные заказы: не восстанавливать;
   - b3 — два источника и больше, расхождение ≤ 5 минут;
   - b4 — источники расходятся больше чем на 5 минут;
   - b5 — ровно один первичный источник;
   - b6 — есть только вторичные источники;
   - b7 — источников нет.

   Кроме групп, выводится число строк по каждому источнику и наибольшее расхождение в секундах.
4. **Появляются ли новые записи без даты после деплоя** (08.11 20:37 UTC). Ожидается 0 в двух колонках:
   - `undated_after_first_dated_post_deploy_row`;
   - `paid_orders_after_deploy_with_undated_purchase`.

## Источники дат
**Первичные.** Записаны самим платежом, ключ — `charge_id` или id заказа:

| Источник | Почему достоверен |
|---|---|
| `shop_orders.paid_at` | `CURRENT_TIMESTAMP` в той же транзакции, что и запись покупки (`_mark_order_paid` + `_record_purchase`) |
| `payment_inbox.paid_at` | Время оплаты от Telegram: дата `successful_payment` или `date` из `getStarTransactions` |
| `subscription_payments.created_at` | В той же транзакции, только подписки Stars |
| `subscription_events.created_at` | Ключ `purchase:<charge_id>`, в той же транзакции, только покупки подписок |

**Вторичные.** Только подсчёт, сами по себе не используются:
- `subscriptions.created_at/starts_at`: в схеме бота это TEXT без DEFAULT, а `starts_at` может быть продолжением прежней подписки;
- `paypal_orders.updated_at`: время последнего изменения, а не оплаты;
- `payment_inbox.received_at`: время получения, при сверке может быть позже оплаты.

**Внешние.** Здесь не запрашиваются, нужен отдельный доступ:
- Telegram `getStarTransactions`: `id` = `charge_id`, `date`;
- Stripe: invoice `status_transitions.paid_at`, `id` = `charge_id`;
- PayPal: capture `create_time`.

- Каждая из семи групп получила ровно ожидаемые строки; сумма групп равна числу записей без даты.
- Запрос 4 нашёл единственную подложенную запись без даты после деплоя.
- Строки в базе не изменились.
